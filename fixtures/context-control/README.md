# Context-control catalog conformance fixtures

These MIT-licensed synthetic fixtures are generated from actual Harness
`ContextBindingDescriptor::seal/validate` and `ContextBindingCatalog::seal/validate`
methods. They contain no private captures, provider output, credentials or game data.
They are test-only inputs, retained in source control and removable with ordinary repository
history retention. They do not authorize execution or identify a trusted deployed owner.

`catalog-conformance.json` uses fixture format v1 and generator
`crates/harness/examples/context_control_catalog.rs` with its adjacent `fixtures.rs`.
Its `origin_revision` pins the original producer contract at
`997821420db5a32d40cd2f07ad8f0ebcafcda96c`; it is not the identity of a later candidate
that generates identical bytes. The actual generator revision, dirty state, source hashes,
binary hash and output hash are written separately under `target/`.

From the repository root, using the pinned toolchain:

```bash
cargo run --locked --example context_control_catalog -- \
  target/control-catalog/catalog-conformance.json \
  target/control-catalog/generation-evidence.json
cmp fixtures/context-control/catalog-conformance.json target/control-catalog/catalog-conformance.json
cargo test --locked --test context_owner_limits
```

For an intentional fixture update, review the generated bytes before copying them into this
directory. Regenerate evidence after committing from a clean checkout, so its actual
`candidate_revision` names the complete source. Dirty evidence records selected source hashes
and tracked-diff/status hashes but is not a reproducible clean revision. The generated output
and evidence paths must differ; use ignored `target/` paths to avoid changing source identity.
Consumer pin adoption and authenticated consumer integration are separate gates.

The fixture contains four full validated catalogs: default, restricted, zero-note and disabled.
Disabled metadata remains present; `descriptor_for` rejects it as unusable. Each descriptor's
digest covers the existing full typed serialization with its digest cleared. The catalog hash
covers the existing `(owner_id, owner_version, descriptors)` tuple encoding. These hashes prove
byte consistency, not trusted authority or freshness.

Twenty-five independent field vectors exercise below minimum, minimum, a restricted value,
global maximum and one over for each advertised limit. Negative `max_notes` fails unsigned wire
decoding; zero is a valid note ceiling. Other zero ceilings and all one-over values fail the
producer limit validator. `descriptor_result` describes descriptor validation only. The fixture
does not encode policy-schema validity, requested counts, or selected-profile execution.
Because this fixture pins its historical contract-origin revision, its vectors cover the five
numeric descriptor fields as they were then; the optional `output_reserve_bytes` added by
[ADR 0058](../../docs/decisions/0058-served-whole-input-output-reserve.md) postdates it, defaults to
absent, and is exercised by the library and served-boundary tests instead.
`context_owner_limits` also tests exact fixture regeneration, mutation of every limit,
stale catalog hashes, invalid sealed members, duplicate identities and closed-field decoding.

The existing v1 descriptor/catalog wire shape and global limits are unchanged. Rendering,
event saturation, recovery under selected limits, Console transport capacity and Studio catalog
validation remain outside this fixture's evidence.
